The two halves of the system

RAG splits into two independent lifecycles. Ingestion (blue) runs once per document, asynchronously in a queue worker — it turns files into searchable vectors. Query (green) runs on every chat message, synchronously inside the HTTP request — it finds the closest vectors and asks GPT to answer from them. They meet at one place only: the embeddings table.

No vector database — and that's deliberate
Vectors are stored as JSON in a plain MySQL longtext column. Similarity is computed in pure PHP (a hand-written cosine() loop), not by a vector engine like pgvector or Pinecone. Every approved, user-visible embedding is loaded into memory and scored per request. Simple and fully inspectable — see Inspecting the pipeline for the scaling caveat.
01

Document upload & storage

Two entry points — admins via POST /admin/documents, faculty/students via POST /faculty/my-documents — both funnel into the same DocumentService::upload(). Upload does not chunk or embed. It only stores the file, writes one documents row at status PENDING, and records a SHA-256 hash to reject byte-for-byte duplicates.

02

Approval → processing → chunking

Chunking is not part of upload. It only happens after an admin approves the document, which flips status to PROCESSING and dispatches ProcessDocumentJob onto the queue. The worker extracts text, slices it into overlapping word windows, and writes one row per chunk into document_chunks.

Trigger point
DocumentService::approve() → ProcessDocumentJob::dispatch($document->id). The job (tries=3, timeout=300s) calls DocumentProcessingService::process(), which orchestrates extract → chunk → embed → mark APPROVED. If all retries fail, status becomes FAILED.
1

Extract text into pages

DocumentTextExtractor::extract() dispatches by file type and returns an array of {page, text}.

PDF → smalot/pdfparser (per-page) · DOCX → ZipArchive + strip word/document.xml · TXT/MD → file_get_contents
2

Slide a fixed word window across each page

Config is expressed in tokens (chunk_size 150, overlap 40) and converted to words via a ~0.75 token-per-word ratio — a window of ~112 words advancing ~72 words at a time.

window = ceil(150 × 0.75) ≈ 112 words · step = window − ceil(40 × 0.75) ≈ 72 words · overlap keeps context across boundaries
3

Persist one row per chunk

Each slice becomes a document_chunks row with a sequential chunk_index, the raw text, an estimated token_count, and optional page/section metadata.

Written by DocumentProcessingService::process() via $document->chunks()->create([...])
ChunkingService.php — sliding window
// token config → word window (~0.75 ratio)
$size    = max(50, config('rag.chunking.chunk_size')); // 150
$overlap = config('rag.chunking.overlap');          // 40
$window  = (int) ceil($size * 0.75);            // ~112 words
$step    = max(1, $window - (int) ceil($overlap*.75));

for ($i = 0; $i < $total; $i += $step) {
    $slice = array_slice($words, $i, $window);
    $chunks[] = [
        'content'     => implode(' ', $slice),
        'token_count' => (int) ceil(count($slice)/.75),
    ];
}

03

Turning chunks into vectors

Immediately after chunking — still inside the same queue job — EmbeddingService::embedDocument() sends the chunk texts to OpenAI in batches of 50 and stores each returned 1536-float vector as JSON in the embeddings table. This is the only point in ingestion where OpenAI is called for document content.

04

Query, similarity search & retrieval

When a user sends a message, the controller persists it immediately, then hands the question to the RAG engine. Retrieval embeds the question, loads every approved + user-visible embedding for the active model, scores each one with an in-PHP cosine similarity, sorts, applies a threshold, and keeps the top 6. There is no SQL similarity — the math runs in application code.

RetrievalService — score, filter, top-K
$queryVector = $this->embeddings->embedQuery($query);

$scored = $candidates->map(fn($e) => [
    'chunk'    => $e->chunk,
    'document' => $e->document,
    'score'    => $this->cosine($queryVector, $e->vector),
])->sortByDesc('score')->values();

$passing = $scored
    ->filter(fn($r) => $r['score'] >= $threshold); // 0.35

// fallback: if none pass, keep the single best > 0
return $passing->take($topK)->values();  // 6
cosine() — pure PHP, no DB math
private function cosine($a, $b): float {
  $len = min(count($a), count($b));
  $dot = $nA = $nB = 0.0;

  for ($i=0; $i<$len; $i++) {
    $dot += $a[$i] * $b[$i];
    $nA  += $a[$i] * $a[$i];
    $nB  += $b[$i] * $b[$i];
  }
  if ($nA <= 0 || $nB <= 0) return 0.0;

  return $dot / (sqrt($nA) * sqrt($nB));
}
Retrieval is access-controlled
Candidates are filtered by Document::scopeApproved() and scopeVisibleTo($user) before any scoring. Students only see embeddings from documents whose visibility JSON contains "students"; faculty see students + faculty; admins see everything. A student can never retrieve a faculty-only document, even if it's the closest vector.

Prompt assembly & answer generation

With the top chunks in hand, RagChatService::buildMessages() assembles a system prompt + numbered context block + recent history + the question, and sends it to gpt-4o at temperature 0.3. The answer, its sources, and a confidence score are stored and returned to Vue as JSON.

The messages array

Exactly what GPT receives

A single messages[] in this order:

  • system — UniNexus persona + the mode prompt + “write entirely in {language}” + citation rules + optional admin override + the Context: block of numbered chunks
  • user/assistant … — up to 6 prior turns for continuity
  • user — the current question, last
Hallucination control

Grounding, not trust

  • Cite-by-bracket: “Answer using the provided context… cite sources by their bracket numbers [1].”
  • No-match honesty: empty context → “No reference documents matched… do not invent citations,” stay on academic topics.
  • Threshold filter: sub-0.35 chunks never reach the prompt.
  • Low temperature: 0.3 reduces drift.

Inspecting & debugging the pipeline

Because everything is plain MySQL + JSON, you can verify each stage with ordinary SQL — no special tooling. Here's how to confirm a document was chunked, embedded, and how to see exactly which chunks a given answer matched.

Verify chunks & embeddings exist
-- did processing run?
SELECT status, processed_at, pages
FROM documents WHERE id = 42;

-- chunk count + a sample
SELECT chunk_index, token_count,
       LEFT(content, 80) AS preview
FROM document_chunks
WHERE document_id = 42
ORDER BY chunk_index;

-- embeddings: model + dims present?
SELECT model, dimensions, COUNT(*)
FROM embeddings
WHERE document_id = 42
GROUP BY model, dimensions;
Trace which chunks an answer used
-- the answer's stored sources + score
SELECT id, confidence, confidence_level,
       JSON_PRETTY(sources)
FROM chat_messages
WHERE role = 'assistant'
ORDER BY id DESC LIMIT 1;

-- relational citations → chunk text
SELECT mc.relevance, d.title,
       LEFT(dc.content, 100) AS chunk
FROM message_citations mc
JOIN documents d       ON d.id  = mc.document_id
JOIN document_chunks dc ON dc.id = mc.document_chunk_id
WHERE mc.chat_message_id = 99
ORDER BY mc.relevance DESC;
Verify in the UI

Confidence + source cards

Every assistant message renders a confidence badge and clickable source cards (title, page, excerpt, score). If sources are empty, the answer came from general knowledge, not your documents.

Tinker

Eloquent introspection

Embedding::find($id)->vector returns the decoded float array. $chunk->embedding and $message->citations traverse the relations directly.

Scaling caveat

In-PHP cosine is O(N)

Every query loads all approved, visible embeddings and scores them in PHP. Fine for hundreds–thousands of chunks; for large corpora you'd move to a real vector index (pgvector / a vector DB).

A note on the response model
Your codebase's configured default answer model is gpt-4o (env OPENAI_MODEL, admin-overridable) — so if you intend gpt-4o-mini, set it in Admin → Settings or .env. The chat_messages.model column records the model actually used for each answer, so you can confirm per-message.
